# Compartilhar certificado inverte o ônus probatório

Construir um módulo "Certificados" no Simples Contábeis é tecnicamente viável, e a parte mais fácil é exatamente a que mais preocupa à primeira vista: um certificado **A1** é só um arquivo `.pfx`/`.p12` protegido por senha, e todo o processo de assinatura (extrair a chave, calcular o hash, gerar o CAdES/PAdES) pode rodar 100% no backend Express, sem navegador, sem plugin e sem hardware — é por isso que o A1 é descrito pelo mercado como "a escolha preferida para integração com sistemas que precisam assinar documentos de forma automaticamente" ([Blog Tecnospeed](https://blog.tecnospeed.com.br/?p=15028)). O problema real não é criptográfico, é jurídico-organizacional: a arquitetura da ICP-Brasil amarra cada certificado a uma única pessoa física "Responsável pelo uso" ([ADE ICP 05.B — PJ v.2.0](https://mailman.iti.gov.br/images/repositorio/legislacao/adendos/ADE-ICP-05.B_-_PJ_-_v.2.0.pdf)), e qualquer assinatura feita com esse certificado é presumida legalmente como sendo dela, sem distinção forense de qual colaborador de fato apertou o botão — centralizar um único e-CNPJ do escritório para múltiplos operadores "usarem via permissão do sistema" concentra 100% do risco de fraude e de disputa trabalhista sobre o sócio nomeado, não sobre quem efetivamente assinou. A arquitetura recomendada, portanto, não é "um certificado A1 com controle de acesso", e sim "um certificado por colaborador autorizado" — o que resolve ao mesmo tempo o problema jurídico e dá ao sistema uma trilha de auditoria que realmente identifica quem assinou o quê. No lado técnico de acesso ao certificado, A1 elimina de uma vez a classe inteira de falhas associadas a token/smartcard (driver, timeout de comunicação USB, sessões remotas) que afeta o A3; as falhas reais a projetar contra são verificação de revogação (OCSP/CRL) indisponível e corrupção de PDF ao re-assinar. O ecossistema Node.js cobre bem a parte básica de PAdES (`@signpdf` + `node-forge`), mas não tem nenhuma biblioteca madura para LTV ou timestamp — e nenhum concorrente (Clicksign, D4Sign, doc9, gov.br) publica como resolveu isso, o que significa que essa parte terá que ser desenhada do zero.

## O A1 roda inteiro no servidor; o A3 nunca sai do token

A razão pela qual nenhuma aplicação web consegue ler diretamente um certificado A3 (token USB ou smartcard) é estrutural, não um detalhe de implementação: a especificação atual da Web Crypto API deixou explicitamente **smart cards fora de escopo** — participantes do próprio grupo de trabalho do W3C registraram que "não há como obter acesso a um smart card se ele não estiver pré-provisionado com um nome específico para uma origem específica" ([W3C public-webcrypto-comments](https://lists.w3.org/Archives/Public/public-webcrypto-comments/2013May/0029.html)), e os mecanismos antigos que contornavam isso — plugins NPAPI e applets Java — foram desativados por todos os grandes navegadores entre 2015 (Chrome 45) e 2017 (Firefox 52) ([Tecnoblog](https://tecnoblog.net/noticias/oracle-fim-plugin-java/); [Blog Bling](https://blog.bling.com.br/applets-java-no-firefox/)). O sucessor funcional desse modelo, hoje padrão em todo o mercado brasileiro de ICP-Brasil (Lacuna Web PKI, BRy Signer, Certisign WebSigner, Vero Signare, SyngularID, GFSIS, Senior SIGN Studio), é a arquitetura de **duas peças**: uma extensão de navegador que, por si só, não acessa hardware algum, mais um **aplicativo nativo complementar instalado no sistema operacional**, com os dois componentes falando via Chrome Native Messaging ou um servidor HTTP em `localhost` — a página web só envia o hash do documento, e a extensão só retorna a assinatura; a chave privada nunca sai do token ([ExtensionAuditor, Vero Signare](https://extensionauditor.com/scan/vero-signare-webpki-gacmlpfmhfphdmjpbhhidbkjceoocmka)). A Lacuna Web PKI segue exatamente esse padrão: a Chrome Web Store descreve a extensão como permitindo "assinatura de documentos no navegador... sem a necessidade de Java", mas o próprio guia de instalação de terceiros avisa que, se a extensão mostrar "Application not fully installed", é preciso baixar e instalar separadamente o app nativo complementar ([eideasy, Lacuna Middleware](https://www.eideasy.com/help/get-started-lacuna)) — o SDK oficial `web-pki` no npm expõe um enum `InstallationStates` justamente para o desenvolvedor tratar programaticamente o caso de a extensão estar presente sem o app nativo ([unpkg.com, web-pki README](https://unpkg.com/web-pki@2.16.3/README.md)).

Para o caso do Simples Contábeis, essa arquitetura de extensão+agente nativo é **irrelevante na prática**, porque ela só é necessária quando o certificado precisa ficar no dispositivo físico do usuário final (A3 em token, ou A1 instalado no keystore do Windows do próprio usuário). O desenho correto para um SaaS de escritório contábil é o inverso: o A1 do colaborador autorizado é **enviado uma vez e guardado no servidor**, criptografado, e toda assinatura subsequente roda no backend sem o navegador precisar fazer nada além de disparar a chamada — nenhuma extensão, nenhum app nativo, nenhuma dependência do que está instalado na máquina do usuário. Isso também evita o problema mais citado de suporte ao vivo com esse modelo: erros de "certificado não encontrado" causados por certificado expirado, driver ausente, token desconectado ou navegador desatualizado ([DocuSign Brasil](https://www.docusign.com/pt-br/blog/certificado-digital-nao-encontrado)). Vale registrar que não foi encontrada evidência de adoção do padrão internacional Cloud Signature Consortium (CSC) por provedores brasileiros — o ecossistema ICP-Brasil construiu sua própria normativa de "certificado em nuvem" (PSC credenciado, LPSC, HSM FIPS 140-2 nível 3, regulado pela IN ITI nº 20/2020) em vez de adotar o padrão europeu ([ConvergênciaDigital](https://convergenciadigital.com.br/especial/cloud/iti-normatiza-o-uso-de-certificao-digital-na-nuvem/)), o que é relevante caso o escritório decida, no futuro, oferecer aos clientes assinar com certificado próprio em nuvem (birdID, SerproID) em vez de A1 custodiado.

## Lei garante presunção plena só ao certificado ICP-Brasil qualificado

A legislação brasileira define três níveis de assinatura eletrônica, e só um deles carrega presunção legal automática de autoria e integridade. O art. 10, §1º da MP 2.200-2/2001 atribui essa presunção exclusivamente a documentos assinados com certificado emitido dentro da ICP-Brasil ([Felsberg Advogados](https://www.felsberg.com.br/assinatura-digital-de-documentos-modalidades-e-cautelas/)); a Lei 14.063/2020 formalizou essa hierarquia em três camadas — **simples** (ex.: marcar uma caixa, clicar "aceitar"), **avançada** (certificados fora da ICP-Brasil ou outro meio aceito pelas partes, vinculado exclusivamente ao signatário) e **qualificada**, definida por remissão direta ao mesmo art. 10, §1º da MP, ou seja, é sinônimo de assinatura digital ICP-Brasil ([Câmara dos Deputados, Lei 14.063/2020](https://www2.camara.leg.br/legin/fed/lei/2020/lei-14063-23-setembro-2020-790659-publicacaooriginal-161547-pl.html)). O efeito prático é uma inversão do ônus da prova: quem contesta uma assinatura qualificada precisa demonstrar vício ou fraude concreta — jurisprudência consolidada exige elementos materiais como boletim de ocorrência de roubo do dispositivo ou invasão comprovada de e-mail, não bastando negativa genérica ([Legale, via resumo de busca](https://legale.com.br/?p=2104202)) — enquanto para as modalidades simples e avançada é quem **apresenta** o documento que precisa provar autoria e integridade, caso a caso. O STJ confirmou essa gradação no REsp 2.159.442/PR: a assinatura avançada tem **validade jurídica idêntica** à qualificada, apenas com peso de prova menor — a lei gradua a prova, não a validade ([Lex.com.br](https://www.lex.com.br/falta-de-credenciamento-da-entidade-certificadora-na-icp-brasil-por-si-so-nao-invalida-assinatura-eletronica/)).

Isso significa que, para a maioria dos documentos de um escritório contábil — TRCT, recibo de férias, ciência de advertência, contratos simples com cliente — **não existe exigência legal expressa de certificado ICP-Brasil**; a Reforma Trabalhista eliminou a homologação sindical da rescisão e não impôs assinatura digital qualificada no seu lugar, e a pesquisa não localizou nenhuma norma (CLT, Lei 14.063/2020, Manual eSocial) que exija ICP-Brasil para a assinatura do TRCT pelo próprio empregado. Já para obrigações transmitidas a órgãos públicos o requisito é oposto e taxativo: eventos do eSocial exigem certificado ICP-Brasil A1 ou A3 do **transmissor** (o escritório/empregador) ([Ajuda Alterdata](https://ajuda.alterdata.com.br/dpbase/esocial-para-envio-do-esocial-e-necessaria-a-utilizacao-de-certificado-digital-60485238.html)), e a Escrituração Contábil Digital (ECD) e Fiscal (ECF) exigem assinatura com certificado ICP-Brasil tanto do contabilista quanto da pessoa jurídica, verificada quanto a validade no momento da transmissão ([Contadores CNT](https://contadores.cnt.br/projetos/34/noticias/tecnicas/2026/04/01/imposto-de-renda-2026-como-contadores-utilizam-certificados-digitais-no-envio-de-declaracoes.html)). O risco documentado de implementar errado não é abstrato: criminosos usaram certificado digital em nome de um juiz para emitir 8 alvarás fraudulentos e desviar mais de R$ 4 milhões da Justiça do Trabalho ([Tecnoblog](https://tecnoblog.net/noticias/certificado-digital-e-usado-para-desviar-r-4-milhoes-da-justica-do-trabalho/)), e entidades do setor (ANCert, AARB) equiparam compartilhar certificado ou senha a "entregar a terceiros um cartão de crédito com a senha", citando casos reais de abertura fraudulenta de empresas e procurações eletrônicas indevidas como consequência ([AMDJus](https://amdjus.com.br/campanha-alerta-para-perigos-do-compartilhamento-de-certificado-digital-entidades-combatem-fraudes-e-golpes-online/)). O padrão de falha mais citado na jurisprudência não é "faltou certificado ICP-Brasil", e sim "faltou trilha de auditoria" — um juiz chegou a questionar a validade de assinaturas via DocuSign por ausência de relatório de validação/certificação ([Migalhas](https://www.migalhas.com.br/depeso/402528/distincoes-entre-assinaturas-digitais-e-eletronicas-pouco-conhecidas)), o que reforça que o módulo precisa gerar evidência robusta independentemente do nível de assinatura escolhido.

## Certificado único para vários colaboradores inverte o ônus da prova

Não existe, nas normas do ITI levantadas nesta pesquisa, uma resolução que proíba literalmente "três funcionários operarem o mesmo arquivo `.pfx`" — mas toda a arquitetura regulatória da ICP-Brasil foi desenhada para o cenário opposto. O Termo de Titularidade define que o titular (pessoa jurídica, via representante legal) nomeia uma pessoa física como "Responsável pelo uso", que é quem responde pela "criação, troca, utilização e proteção das senhas, chave privada e da mídia que as contém" ([ADE ICP 05.B — PJ v.2.0](https://mailman.iti.gov.br/images/repositorio/legislacao/adendos/ADE-ICP-05.B_-_PJ_-_v.2.0.pdf); [Termo de titularidade, ITI](https://mailman.iti.gov.br/images/repositorio/legislacao/adendos/ADE_ICP-05.B-_PF_-_v_2.0_.pdf)). A Resolução CG-ICP Brasil nº 79/2010 chega a vedar expressamente qualquer procuração para a função de Responsável pelo uso no caso de pessoa física — "vedada qualquer espécie de procuração para a sua função" —, justamente para reduzir fraude, incluindo "a emissão de um certificado digital em nome de outrem" ([ARPEN-SP](https://arpensp.org.br/noticia/15364)); mesmo para pessoa jurídica, a representação só vale com procuração **pública**, com poderes específicos para atuar perante a ICP-Brasil. O espírito da norma pressupõe correspondência 1:1 entre quem detém a chave e quem responde por ela — o que a torna hostil à ideia de múltiplos operadores humanos atrás de um único certificado, mesmo sem uma frase proibitiva endereçando esse cenário exato de "sistema interno com permissionamento".

A consequência prática é o que a pesquisa identifica como um problema de **não-repúdio invertido**: como a assinatura ICP-Brasil goza de presunção legal de validade atribuída ao titular, se o colaborador B ou C usar o certificado do escritório para assinar algo indevido, juridicamente "foi o Responsável nomeado quem assinou" — o sistema jurídico não reconhece "o funcionário B assinou usando permissão do sistema", reconhece apenas "o certificado assinou". O ônus de provar que não foi ele recai sobre o sócio/contador nomeado, não sobre quem de fato operou o sistema ([AMDJus](https://amdjus.com.br/campanha-alerta-para-perigos-do-compartilhamento-de-certificado-digital-entidades-combatem-fraudes-e-golpes-online/)). É sintomático que a própria Fenacon — entidade de classe dos escritórios contábeis — reconheça que a guarda de múltiplos certificados **de clientes** por um escritório já gera "vulnerabilidade a riscos" e recomende que o escritório use **seu próprio** certificado em vez do de cada cliente para operações externas; essa recomendação resolve um problema diferente (substituir N certificados de terceiros por 1 do escritório para a Receita Federal, por exemplo), não endossa múltiplos funcionários operando esse único certificado internamente. A alternativa — cada colaborador autorizado com seu próprio e-CPF — resolve exatamente essa ambiguidade: com certificado individual, "o certificado assinou" e "a pessoa Z assinou" voltam a coincidir, e o sistema pode registrar, de forma juridicamente defensável, identificador do usuário, titular e número de série do certificado, timestamp da assinatura, resultado da verificação OCSP/CRL no momento e hash do documento antes/depois — o conjunto mínimo de campos que a lógica da presunção legal exige para que o escritório consiga provar, se contestado, exatamente quem assinou o quê. Vale notar que um relatório de Análise de Impacto Regulatório do próprio ITI identifica como problema regulatório conhecido a exigência atual de um único responsável por certificado de pessoa jurídica, e avalia extinguir o A1 de pessoa jurídica em favor de "selos eletrônicos" — mudança ainda não confirmada como adotada, mas que sinaliza que o próprio regulador já reconhece a fragilidade desse modelo de titular único ([Relatório de AIR, gov.br/ITI](https://www.gov.br/iti/pt-br/assuntos/legislacao/analise-de-impacto-regulatorio-air-e-avaliacao-de-resultado-regulatorio-arr/Relatorio_de_AIR___Pauta_modernizante.pdf)).

## OCSP fora do ar e PDF corrompido são as falhas reais, não o certificado

Como o módulo "não pode falhar, travar ou dar erro de comunicação", vale mapear onde integrações reais de assinatura digital de fato quebram em produção — e a resposta consistente nas fontes é que as duas causas mais citadas são **dependências externas de rede e hardware**, não a lógica de assinatura em si. A primeira é falha na verificação de revogação: "Failed to retrieve CRL information" ocorre quando tanto o responder OCSP quanto a CRL falham, por URL de revogação inválida, ausência de resposta ou bloqueio de firewall/proxy ([eSign Celfocus](https://docs.esign.celfocus.com/esign/1.8.x/troubleshooting/ocspcrlfail.html)); um guia chega a documentar uma flag `signing.revocation.skip` para desativar essa verificação, mas recomenda explicitamente **não usá-la em produção**. Um padrão de design relevante vem do PingFederate: seu timeout padrão de responder OCSP é de 5 segundos, e por padrão trata um responder inalcançável como **válido** (fail-open) em vez de travar a operação inteira ([PingFederate docs](https://docs.pingidentity.com/pingfederate/11.2/administrators_reference_guide/help_certificaterevocationcheckingtasklet_managecertificaterevocationstate.html)) — uma troca de segurança por disponibilidade que precisa ser avaliada com cuidado, mas que é a referência concreta mais citada contra "o sistema trava porque a ICP-Brasil está fora do ar". A segunda causa recorrente é específica de certificado A3/hardware (token, smartcard) — timeout de driver, perda de sessão em RDP/Citrix, falha silenciosa sem mensagem de erro ([arXiv 1209.2457](https://arxiv.org/pdf/1209.2457); [Citrix support](https://support.citrix.com/external/article/CTX475126/safenet-smart-card-unable-to-use-this.html)) — e é justamente essa classe de falha que a decisão de usar A1 server-side **elimina por completo**, um argumento técnico adicional, independente do argumento jurídico, a favor do A1 custodiado para estabilidade de produção.

A terceira causa, menos óbvia e mais perigosa por ser silenciosa, é corrupção de PDF ao adicionar assinaturas: um ticket de prioridade "Blocker" no Apache PDFBox documentou que adicionar uma assinatura visível a um PDF já certificado faz o Acrobat reportar a certificação anterior como corrompida ([PDFBOX-3699](https://issues-test.apache.org/jira/browse/PDFBOX-3699)); em outro relato, assinar PDFs resultantes de merge de múltiplos documentos invalidou todas as assinaturas exceto a última, resolvido só depois de remover o outline do PDF antes de assinar ([Adobe Community](https://community.adobe.com/t5/acrobat-discussions/signature-cause-quot-invalidation-quot-of-previous-sigs/m-p/15208241/highlight/true)). Como o Simples Contábiis já faz merge de PDFs com `pdf-lib`, essa superfície de risco é diretamente relevante e deveria ser testada explicitamente antes de produção: assinar PDFs com estrutura complexa (merge, anotações, criptografia, assinatura sequencial múltipla) é onde os bugs de PAdES concentram-se, segundo os achados de rejeição de validador listados (array `/ByteRange` com placeholder zerado, campo `/M` malformado, `/Encrypt` perdido em atualização incremental) ([Loslab](https://blog.loslab.com/en-gb/pdfium-component/why-pdf-validators-reject-pades-signatures-pdfium-delphi.html)). Uma quarta causa é contenção de acesso concorrente ao mesmo recurso de chave: um issue do OpenSC relatou falhas intermitentes ao usar a mesma identidade de assinatura em processos paralelos, corrigido serializando o acesso para que apenas um processo use a chave por vez ([OpenSC #1983](https://www.github.com/OpenSC/OpenSC/issues/1983)) — relevante se o módulo permitir múltiplos colaboradores assinando simultaneamente com certificados distintos (sem problema, cada um é um arquivo separado) ou, pior, tentando usar o mesmo P12 ao mesmo tempo (exatamente o cenário que a recomendação de certificado individual evita). Sobre como plataformas maduras mitigam essas falhas, a pesquisa encontrou evidência direta só para o Docusign, e o padrão lá é "fail visibly and let a human retry": retry manual orientado por suporte quando o certificado aparece como revogado por indisponibilidade temporária da base ([Docusign Community #10558](https://community.docusign.com/questions/10558)), envelope automaticamente invalidado ("voided") ao expirar sem fila de reenvio automática, e bloqueio do envelope até reenvio manual do remetente após falha de autenticação. Não foi encontrada nenhuma documentação pública de engenharia de confiabilidade da Clicksign, D4Sign ou do assinador gov.br sobre esse tema — o que significa que, para o módulo do Simples Contábeis, erro visível + botão de retry manual (em vez de retry automático silencioso) é tanto o padrão de mercado observável quanto a opção mais segura para evitar duplo envio ou assinatura.

## Node.js cobre o PAdES básico; LTV e timestamp ficam por conta própria

Para assinatura PAdES de PDF em Node, o ecossistema convergiu para a família `@signpdf/*` — sucessora do antigo `node-signpdf`, hoje formalmente deprecated no npm em favor de `@signpdf` ([npm registry node-signpdf](https://registry.npmjs.org/node-signpdf)) — com a última versão de `@signpdf/signpdf` publicada em 2025-12-29 e o repositório com push recente em 2026-10-07, ou seja, ativamente mantido ([GitHub vbuch/node-signpdf](https://github.com/vbuch/node-signpdf)). A arquitetura é modular: `@signpdf/signpdf` entende a estrutura do PDF, `@signpdf/signer-p12` lê o arquivo P12 usando `node-forge` por baixo, e helpers de placeholder separados cobrem geração de PDF via `pdfkit` (que o projeto já parece usar via `pdf-lib`) ou um placeholder genérico descrito pelos próprios mantenedores como "rather fragile". Conformidade PAdES é documentada via o `SubFilter` `ETSI.CAdES.detached` no dicionário de assinatura. O ponto crítico é o que **falta**: não há suporte a LTV (Long-Term Validation, que embute a cadeia completa e a resposta OCSP/CRL no PDF) em nenhuma biblioteca JS encontrada, e timestamp/TSA só existe num pacote de terceiro (`@dotit/pades`) com download muito baixo, tratado como opção nicho não validada em produção ([socket.dev @dotit/pades](https://socket.dev/npm/package/@dotit/pades)). Isso significa que, se o escritório precisar de PAdES com validade de longo prazo (relevante para documentos que precisam continuar verificáveis mesmo após a expiração do certificado do colaborador), essa camada terá que ser implementada manualmente por cima do `@signpdf`, ou delegada a uma API comercial como a Lacuna REST PKI.

Para as primitivas de baixo nível, `node-forge` (5.337 estrelas, push em 2026-09-25, release npm em 2026-03-24) e `pkijs` (1.400 estrelas, push em 2026-09-30, construído sobre WebCrypto, exige Node 16+) são as duas opções maduras para carregar PKCS#12, extrair a chave privada e montar CMS/PKCS#7 — não há um pacote "CAdES" turnkey em JavaScript, a estrutura precisa ser montada manualmente com um dos dois ([GitHub digitalbazaar/forge](https://github.com/digitalbazaar/forge); [GitHub PeculiarVentures/PKI.js](https://github.com/PeculiarVentures/PKI.js)). Para checagem de revogação, `easy-ocsp` é a opção mantida mais recente (release em 2026-05-24, embora pequena, mantenedor único) enquanto o concorrente `ocsp-hashes` está classificado como inativo há mais de 12 meses; para CRL não existe pacote dedicado maduro, e a alternativa prática é usar as funções de CRL já presentes no próprio `pkijs` ([Snyk Advisor ocsp-hashes](https://security.snyk.io/package/npm/ocsp-hashes); [GitHub PeculiarVentures/PKI.js](https://github.com/PeculiarVentures/PKI.js)). Um gap de ecossistema relevante para quem precisa identificar automaticamente CPF/CNPJ de um certificado: não existe nenhum pacote npm dedicado a extrair esses dados via OID da Subject Alternative Name do padrão ICP-Brasil — só existem libs genéricas de validação de string de CPF/CNPJ, sem relação com certificados — então esse parsing (via `node-forge` ou `pkijs`, procurando o `otherName` dentro de `subjectAltName`) precisará ser escrito à mão. Entre as rotas comerciais, a Lacuna Software é a única com SDK Node.js oficial e publicado no npm (`restpki-client`, mantido pela própria empresa, última versão em 2025-12-09), com múltiplos produtos relacionados (REST PKI, REST PKI Core, PKI Express, Signer, CloudHub) todos com clients Node no GitHub da organização ([npm registry restpki-client](https://registry.npmjs.org/restpki-client)) — vale uma avaliação direta de qual desses produtos aceita "certificado fornecido pelo próprio cliente via API" (o modelo que o Simples Contábeis precisa) versus "certificado em nuvem gerenciado pela Lacuna", distinção que a documentação pública não deixou clara nesta pesquisa.

## doc9, Clicksign e D4Sign terceirizam o problema do acesso ao certificado

As quatro referências de mercado pedidas resolvem o acesso ao certificado de formas estruturalmente diferentes, e nenhuma delas é um blueprint direto para "um A1 custodiado no servidor, operado por múltiplos colaboradores via permissão". O **doc9 (Whom.doc9)** nem é uma plataforma de assinatura — é descrito pelo próprio site como "o primeiro gerenciador de certificados digitais em nuvem do Brasil", uma camada de governança sobre certificados que a organização já possui, que "centraliza, rastreia e libera o uso dos seus certificados com controle total sobre quem acessa, o quê e quando" ([lp.doc9.com.br/whom-doc9](https://lp.doc9.com.br/whom-doc9)) — ou seja, é o produto comercial mais próximo conceitualmente do que o Simples Contábeis quer construir, mas o site nunca confirma o termo "ICP-Brasil" nem explica o mecanismo técnico de liberação (proxy server-side, cofre de senha com automação, HSM compartilhado); essa é uma lacuna real que só contato comercial direto resolveria.

A **Clicksign** trata certificado ICP-Brasil como apenas um entre vários métodos de autenticação de assinatura — ao lado de selfie dinâmica, código via WhatsApp, SMS e Pix — disponível mesmo no plano de entrada ("Start": "Assine com Certificado Digital") ([Cora, sobre a Clicksign](https://www.cora.com.br/blog/clicksign-como-funciona/)), confirmando aceitar certificado "em nuvem ou em token" para atender exigências do CFM em laudos médicos ([clicksign.com/lp/icp-saude](https://clicksign.com/lp/icp-saude)) — mas a documentação pública não detalha se isso passa por uma extensão de navegador tipo Web PKI ou por integração server-to-server com o provedor de nuvem. A **D4Sign** tem um indício mais forte, embora não confirmado diretamente pela empresa: sua seção de desenvolvedores linka para "Web PKI" — a extensão da Lacuna Software — cujo mecanismo genérico documentado por terceiros é "a página web chama a extensão via eventos customizados do navegador, e a extensão repassa o pedido para um componente nativo instalado no computador via native messaging", hoje distribuído sob a marca "Web Signer" pela Softplan ([extensionauditor.com, Web PKI](https://extensionauditor.com/scan/web-pki-dcngeagmmhegagicpcmpinaoklddcgon)) — ou seja, para o caminho ICP-Brasil, a D4Sign provavelmente herda a mesma arquitetura extensão+app nativo descrita na primeira seção deste relatório, só que no lado do signatário final, não no lado do escritório.

O caso mais informativo por contraste é o **assinador gov.br/ITI**: ele explicitamente **não** usa o e-CPF/e-CNPJ ICP-Brasil tradicional do cidadão. Ao assinar, "um certificado digital avançado é emitido automaticamente e de forma gratuita" e fica "armazenado na infraestrutura do próprio Instituto Nacional de Tecnologia da Informação (ITI)" ([gov.br/iti, assinatura eletrônica avançada](https://www.gov.br/iti/pt-br/assuntos/assinatura-eletronica-avancada)) — um certificado custodiado e emitido pelo próprio governo, vinculado à identidade da conta gov.br nível prata/ouro, classificado como assinatura **avançada**, não qualificada. É, estruturalmente, o modelo mais parecido com o que o Simples Contábeis consideraria se decidisse não perseguir a presunção legal plena da ICP-Brasil: identidade validada da conta + certificado técnico emitido e guardado pela própria plataforma, sem exigir hardware nem extensão do usuário — mas com nível de confiabilidade jurídica inferior ao qualificado, como a Lei 14.063/2020 deixa explícito. Nenhuma das quatro plataformas publica, em conteúdo acessível, um relato de engenharia sobre retry de OCSP, filas de reprocessamento ou alertas proativos de expiração de certificado como recurso de produto documentado — essa é uma lacuna consistente em todas as fontes consultadas, e não um problema isolado de uma plataforma.

## Arquitetura recomendada e o que falta confirmar antes de implementar

A arquitetura recomendada para o módulo "Certificados" tem quatro pilares. Primeiro, **certificado A1 individual por colaborador autorizado**, não um único e-CNPJ do escritório compartilhado via permissão — cada colaborador habilitado a assinar precisa ter seu próprio e-CPF cadastrado no sistema, mesmo que isso signifique o escritório custear ou orientar a emissão desses certificados; isso resolve diretamente o problema de não-repúdio invertido identificado na seção 3, e é a única forma de o log do sistema registrar "a pessoa Z assinou" em vez de apenas "o certificado assinou". Segundo, **custódia server-side do `.pfx` por usuário**, criptografado em repouso (reaproveitando, na implementação, o padrão de carregamento de certificado que o módulo `nfse.ts` do projeto provavelmente já resolveu para NFe/NFSe), com controle de acesso granular — quem pode assinar o quê, não apenas um botão "assinar" exposto a todo o escritório. Terceiro, **trilha de auditoria append-only** registrando, no mínimo: identificador do usuário que disparou a ação, titular e número de série do certificado usado, timestamp da assinatura (idealmente com carimbo RFC 3161/TSA, já que nenhuma lib JS encontrada faz isso automaticamente), resultado da verificação OCSP/CRL no momento, e hash do documento antes e depois da assinatura — esse conjunto não vem de uma norma brasileira específica (não foi encontrada nenhuma), mas decorre diretamente da lógica da presunção legal de validade: é o que permite ao escritório provar, se contestado, exatamente quem assinou. Quarto, **design fail-visible com timeout agressivo**, não fail-silent nem bloqueio indefinido: timeout curto (segundos, não minutos) na checagem OCSP com fallback para CRL e, se ambos falharem, erro visível ao usuário com opção de retry manual — replicando o padrão observado no Docusign — em vez de perseguir 100% de automação de recuperação, que nenhum concorrente pesquisado parece ter resolvido de forma documentada.

Dito isso, ficaram gaps concretos que não devem ser decididos só com esta pesquisa. Juridicamente, não foi confirmada a redação vigente (pós Resolução 177/2020, DOC-ICP-05 v.6.x) da cláusula sobre vedação de procuração para a função de Responsável pelo uso — a pesquisa só localizou a versão de 2010; isso deveria ser verificado diretamente no texto consolidado do DOC-ICP-05 no site do ITI, ou com um advogado especializado em direito digital/ICP-Brasil, antes de qualquer peça formal ou contrato de serviço que mencione o módulo. Também não há jurisprudência encontrada especificamente sobre "funcionário autorizado via sistema interno usou certificado do empregador e a assinatura foi contestada" — o material disponível trata de fraude externa, não desse cenário de permissionamento interno, o que é exatamente o cenário de risco do design "um certificado, múltiplos operadores" que este relatório recomenda evitar; um parecer jurídico direcionado a esse cenário específico reduziria a incerteza residual mesmo na arquitetura "certificado individual" (ex.: quando o colaborador assina documento de um cliente terceiro, que tipo de procuração/representação é necessária). Tecnicamente, o maior gap é comercial: não foi possível confirmar, na documentação pública, se algum produto da Lacuna Software (REST PKI, REST PKI Core, Signer, CloudHub) aceita nativamente "certificado fornecido pelo próprio escritório, custodiado localmente" como modelo de uso, ou se todos pressupõem certificado em nuvem gerenciado pela própria Lacuna — um contato comercial direto com a Lacuna (ou com a BRy, cujo portal de desenvolvedor não foi localizado nesta pesquisa) esclareceria se vale a pena usar a API comercial para a camada de LTV/timestamp em vez de construir isso manualmente sobre `@signpdf`/`pkijs`.

A implicação mais ampla desta pesquisa é que o desafio de engenharia do módulo "Certificados" não está onde a intuição inicial sugeriria — não é "como assinar um PDF em Node" (isso o ecossistema resolve razoavelmente bem) nem "como acessar um token A3 do navegador" (irrelevante se o design for A1 custodiado). O desafio real é modelar identidade e responsabilidade de forma que coincida com o que a lei brasileira já presume sobre certificados digitais: um certificado, um titular, uma responsabilidade. Desenhar o sistema de permissões em torno dessa equivalência — em vez de tratá-la como um detalhe de controle de acesso a ser resolvido depois — é o que separa um módulo que funciona tecnicamente de um que também resiste a ser contestado em juízo.
