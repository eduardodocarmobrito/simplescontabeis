# Acesso técnico a certificados digitais ICP-Brasil (A1/A3) por aplicações web

## Por que o JavaScript do navegador não pode ler diretamente um certificado A3 (token/smartcard)? Quais modelos de segurança bloqueiam isso, e desde quando (histórico NPAPI/applet Java)?

### Takeaway
Navegadores modernos não expõem nenhuma API JavaScript nativa que alcance um token USB/smartcard: a geração atual da Web Crypto API deixou explicitamente smart cards fora de escopo, e os mecanismos antigos que permitiam esse acesso (plugins NPAPI e applets Java) foram desativados por todos os grandes navegadores entre 2015 e 2017 por razões de segurança (sandboxing/isolamento de processo), forçando o mercado a migrar para extensões de navegador que falam com um processo nativo local.

### Cited Findings
- Durante a elaboração da especificação W3C Web Crypto API, participantes do grupo de trabalho relataram que fornecedores de navegadores consideravam suporte a smart cards "fora de escopo, ao menos na primeira versão da especificação" — [W3C public-webcrypto-comments mailing list](https://lists.w3.org/Archives/Public/public-webcrypto-comments/2013May/0029.html)
- A Web Crypto API atual "não impede o uso de smart cards para operações criptográficas, mas também não há como obter acesso a um smart card se ele não estiver pré-provisionado com um nome específico para uma origem específica" — [W3C public-webcrypto-comments mailing list](https://lists.w3.org/Archives/Public/public-webcrypto-comments/2013May/0029.html)
- Um participante do grupo W3C apontou o conflito estrutural: "smart cards atuais usam AppIDs registrados (ISO7816 AID) para identificar aplicações, um namespace totalmente não relacionado a origens web", citando o FIDO como exemplo de hardware que se adaptou ao modelo de segurança da web em vez do contrário — [W3C public-webcrypto mailing list](https://lists.w3.org/Archives/Public/public-webcrypto/2013May/0094.html)
- O Google Chrome removeu o suporte a plugins NPAPI (a tecnologia usada pelos applets Java de acesso a certificados) com o lançamento do Chrome 45, em 2015 — [Tecnoblog](https://tecnoblog.net/noticias/oracle-fim-plugin-java/)
- A Mozilla anunciou que o Firefox 52 (lançado em março de 2017) abandonaria o suporte a todos os plugins NPAPI, incluindo Java — [Blog Bling](https://blog.bling.com.br/applets-java-no-firefox/)
- A Oracle marcou formalmente as APIs de applet Java para remoção através do JEP-398, após anos de avisos de descontinuação prévios no JEP-289 — [InfoQ, "end of applets"](https://www.infoq.com/news/2021/03/end-of-applets/)
- Sistemas brasileiros que dependiam de applets Java para acesso a certificado precisaram migrar: o e-SAJ do TJMS criou o "Web Signer" como plugin substituto do applet Java para login e peticionamento, avisando que a versão antiga só funcionaria mais no Internet Explorer 11 — [Sedep](https://www.sedep.com.br/?p=69425)
- A Censec (sistema dos cartórios brasileiros) passou a usar um componente próprio de comunicação com certificados digitais compatível com os principais navegadores, abandonando o applet antigo — [PortalDori](https://portaldori.com.br/2017/01/25/cnbcf-divulga-procedimento-de-instalacao-de-novo-applet-na-censec/)
- Para emissão de NF-e com certificados A1/A3 no Firefox pós-NPAPI, era necessário alternar manualmente o modo de acesso ao certificado de "navegador" para "aplicação" — [Blog Bling](https://blog.bling.com.br/applets-java-no-firefox/)

### Inferences
- A combinação de (a) ausência de API padrão de acesso a smart card na Web Crypto API e (b) desativação dos plugins NPAPI/applets Java entre 2015-2017 é a causa raiz técnica direta de por que, hoje, nenhuma aplicação web pode chamar `crypto.subtle` ou qualquer API DOM nativa para ler um certificado A3 num token/smartcard — o acesso só é possível saindo do sandbox do navegador via um componente externo (extensão + processo nativo local, ou app desktop separado).
- O problema de mapeamento de namespace (AID do smartcard vs. origem web) citado pelos engenheiros do W3C explica por que a solução de mercado teve que ser arquitetural (um agente local que faz a ponte) em vez de uma solução pura de API de navegador.

### Gaps
- Não foi possível confirmar nesta pesquisa se alguma extensão do W3C Web Crypto API (ex.: "Web Crypto Key Discovery", mencionado como proposta não implementada) avançou formalmente em alguma versão recente de browser até 2026.

## Quais são os mecanismos reais atuais (2025-2026) usados no mercado brasileiro: extensões de navegador, middleware/agente local via localhost, applets Java (legado) e APIs de assinatura em nuvem/HSM?

### Takeaway
O mercado brasileiro hoje se divide essencialmente em dois modelos vivos — (1) extensão de navegador + aplicativo nativo local complementar (companion app), que se comunica via Chrome Native Messaging ou um servidor HTTP local em localhost, usado para certificados A1 instalados e A3 em token/smartcard; e (2) certificado em nuvem, que elimina o hardware local e usa autenticação OTP/biometria contra um HSM remoto do Prestador de Serviço de Confiança — enquanto applets Java são tecnologia legada morta desde ~2015-2017.

### Cited Findings
- O padrão arquitetural identificado em múltiplas extensões brasileiras de assinatura (Vero Signare, SyngularID, GFSIS) é: a extensão de navegador se comunica com um host nativo instalado no computador via protocolo Chrome Native Messaging; o host nativo acessa o token via PKCS#11; o site/página web envia apenas o hash do documento, e a extensão retorna apenas a assinatura (a chave privada nunca sai do token) — [ExtensionAuditor, Vero Signare scan](https://extensionauditor.com/scan/vero-signare-webpki-gacmlpfmhfphdmjpbhhidbkjceoocmka)
- A extensão "SyngularID" exige instalação em duas etapas — plugin no navegador e, depois, download/instalação de um módulo separado no computador — [Chromeboard, listagem da extensão](https://chromeboard.com/extension/assinatura-digital-no-nav-ccfeeinmndbnfdodejnonelofajfnakm)
- A plataforma Senior (SIGN Studio) usa um "Agente Desktop" local: ele detecta o token conectado, lista os certificados disponíveis e executa a assinatura localmente, de forma que a chave privada nunca saia do dispositivo; requer Windows 11+ e o driver do token (PKCS#11, ex.: SafeSign, eToken, IDPrime, Watchdata, Serpro) pré-instalado — [Documentação Senior, ativação do Agente Desktop](https://documentacao.senior.com.br/seniorxplatform/manual-do-usuario/sign-studio/certificado-digital/ativacao-agente-desktop.htm)
- No fluxo da Senior, o usuário escolhe a opção A3, confirma que o agente está em execução, espera a página web se conectar a ele, e então clica em confirmar — [Documentação Senior, assinatura com certificado digital](https://documentacao.senior.com.br/seniorxplatform/manual-do-usuario/sign-studio/certificado-digital/assinatura-com-certificado-digital.htm)
- Um usuário relatou em fórum que o assinador desktop do Serpro para A3 só funcionava em Chrome ou Edge, e que o portal verifica um endereço local numa porta específica (65166) — [Fórum Contábeis](https://www.contabeis.com.br/forum/tecnologia-contabil/383579/assinador-serpro/)
- A BRy oferece o "BRy Signer", um assinador de documentos gratuito compatível com certificados ICP-Brasil ou de qualquer outra AC, que verifica validade, cadeia de confiança e revogação do certificado; o usuário pode escolher instalar o certificado no computador, em token USB ou em cartão smartcard — [Baguete](https://www.baguete.com.br/noticias/bry-lanca-assinador-digital-gratuito)
- Causas comuns de erro "certificado não encontrado" em fluxos de assinatura via navegador: certificado expirado, token não reconhecido/sem driver, dispositivo físico desconectado, navegador desatualizado — [DocuSign Brasil, blog](https://www.docusign.com/pt-br/blog/certificado-digital-nao-encontrado)
- Applets Java foram formalmente descontinuados pela Oracle via JEP-398 e não têm suporte em navegadores modernos desde 2015-2017 (ver seção anterior) — são tratados nas fontes levantadas apenas como contexto histórico/legado, sem nenhuma evidência de uso corrente em 2025-2026 — [InfoQ](https://www.infoq.com/news/2021/03/end-of-applets/)
- Não foi localizada, nesta pesquisa, nenhuma evidência de adoção do padrão internacional Cloud Signature Consortium (CSC) API por provedores brasileiros de ICP-Brasil; os resultados de busca sobre CSC API retornaram exclusivamente contexto europeu (eIDAS, SSL.com eSigner, DigiCert, BankID Noruega), sem nenhuma menção ao Brasil ou à ICP-Brasil — [Ascertia, Understanding CSC v2.0](https://blog.ascertia.com/cloud-signature-consortium-2); [Cloud Signature Consortium, CSC API v2.2](https://cloudsignatureconsortium.org/resources/csc-api-v2-2/)

### Inferences
- O modelo "extensão de navegador + companion app nativo falando via Native Messaging/localhost" é hoje o sucessor direto e funcionalmente equivalente do antigo applet Java: resolve o mesmo problema (acesso a hardware criptográfico fora do sandbox do navegador) com uma arquitetura que sobrevive à remoção do NPAPI.
- A ausência de qualquer evidência de CSC API no Brasil sugere que o ecossistema ICP-Brasil desenvolveu sua própria solução de "assinatura remota" (o certificado em nuvem regulado pelo ITI) em vez de adotar o padrão europeu, provavelmente porque a infraestrutura de credenciamento ICP-Brasil (AC Raiz, LPSC) já preexistia e tinha outro desenho normativo.

### Gaps
- Não foi possível confirmar, dentro do orçamento de busca desta pesquisa, se Manifest V3 do Chrome alterou ou restringiu de alguma forma a API Native Messaging usada por essas extensões (a documentação oficial do Chrome sobre Native Messaging retornada na busca não menciona nenhuma mudança relevante relacionada a MV3, nem data de descontinuação do mecanismo) — [Chrome Developers, Native Messaging](https://developer.chrome.com/docs/extensions/mv3/nativeMessaging).
- Não há dados quantitativos (market share) comparando o volume de uso de extensão+agente local vs. certificado em nuvem no mercado brasileiro em 2025-2026; as fontes encontradas (editais públicos, estudos técnicos preliminares de órgãos) são qualitativas e conflitantes — um estudo afirma que "A3 é o tipo de certificado mais utilizado pelos usuários finais" sem citar números de mercado, enquanto outro aponta vantagem de custo da nuvem (e-CPF nuvem ~R$89,90 vs. R$150-413 para token) — [Estudo técnico IFPI/universidade federal citado em busca]; necessita confirmação direta com ITI/ANCD.

## O que é o "Certificado Digital em Nuvem" (ITI/Serpro, birdID, Soluti Nuvem, Safeweb Nuvem etc.)? Como funciona tecnicamente, e ele elimina a necessidade de hardware local/extensão?

### Takeaway
O certificado em nuvem é juridicamente o mesmo e-CPF/e-CNPJ, mas com a chave privada armazenada e operada dentro de um HSM remoto certificado (FIPS 140-2 nível 3) de um Prestador de Serviço de Confiança (PSC) credenciado pelo ITI; o acesso se dá por app móvel com código OTP, segundo fator biométrico ou integração via API/OAuth — e isso efetivamente elimina a necessidade de token/smartcard físico e, na maioria dos fluxos de uso via app, também elimina a necessidade de extensão de navegador, embora integrações empresariais via API ainda dependam de infraestrutura de desenvolvedor própria do provedor.

### Cited Findings
- No modelo em nuvem, a chave privada fica protegida em um HSM remoto operado por uma Autoridade Certificadora credenciada pela ICP-Brasil, e o acesso é feito pela internet com verificação em dois fatores, biometria ou integração por API — [Blog Tecnospeed](https://blog.tecnospeed.com.br/certificado-digital-na-nuvem)
- Juridicamente, o certificado em nuvem é o mesmo e-CPF ou e-CNPJ emitido por uma AC credenciada pela ICP-Brasil, mudando apenas a forma de armazenamento — [Blog Tecnospeed](https://blog.tecnospeed.com.br/certificado-digital-na-nuvem)
- O ITI normatizou esse modelo por meio de instrução normativa/portaria que criou a Lista de Prestadores de Serviço de Confiança (LPSC); aplicações acessam a LPSC para localizar e se conectar aos PSCs credenciados pela ICP-Brasil — [ConvergênciaDigital](https://convergenciadigital.com.br/especial/cloud/iti-normatiza-o-uso-de-certificao-digital-na-nuvem/)
- A IN ITI nº 20/2020 aprovou a versão 3.0 do DOC-ICP-17.01 (Procedimentos Operacionais Mínimos para Prestadores de Serviço de Confiança), consolidando os requisitos normativos do modelo PSC — [IN 20/2020, texto oficial no gov.br/iti](https://www.gov.br/iti/pt-br/assuntos/legislacao/instrucoes-normativas/IN_20_2020_DOC_17.01_assinada.pdf)
- A Portaria nº 2 do ITI (DOU) atualizou os requisitos para serviços de confiança de uso de chaves criptográficas e definiu a LPSC, publicada no site do ITI e em XML assinado no repositório da AC Raiz — [ConvergênciaDigital](https://convergenciadigital.com.br/especial/cloud/iti-normatiza-o-uso-de-certificao-digital-na-nuvem/)
- Normas recentes exigem que os HSMs usados pelos provedores homologados tenham certificação FIPS 140-2 nível 3 — [Jucees-ES, "Tipos Certificado Digital V5"](https://jucees.es.gov.br/Media/Jucees/Manuais%20e%20Procedimentos/Tutoriais/Tipos_Certificado_Digital_V5.pdf)
- O Portal e-CAC da Receita Federal (projeto "Receita na Palma da Mão") foi a primeira aplicação adaptada para aceitar certificados digitais em nuvem de qualquer fornecedor credenciado junto ao ITI — [Netcpa](https://netcpa.com.br/noticias/receita-na-palma-da-mao-adocao-do-certificado-digital-em-nuvem/2570)
- O birdID (Soluti) é descrito como certificado digital em nuvem ICP-Brasil que permite assinar documentos diretamente no app, com validade jurídica equivalente a firma reconhecida em cartório; o app gera um código OTP a cada 30 segundos usado para autorizar operações, e a sincronização do app com a conta é feita lendo um QR Code exibido no portal — [Manuais Soluti, "Como funciona" / "Aplicativo Bird ID"](https://manuais.soluti.com.br/bird-id/recarga-bird-id/como-funciona)
- O modelo comercial do birdID é por consumo de créditos (pacotes de autenticações/assinaturas com validade), embora a emissão do certificado em si seja gratuita — [Manuais Soluti](https://manuais.soluti.com.br/bird-id/recarga-bird-id/como-funciona)
- O certificado em nuvem do Serpro foi renomeado para "SerproID"; funciona via app em vez de hardware, pode ser e-CPF ou e-CNPJ, sempre em versão A3, com validade de até 3 anos — [Serpro, notícia oficial](https://serpro.gov.br/menu/noticias/noticias-2024/serproid-certificado-digital-nuvem)
- Para integração de sistemas externos ao certificado em nuvem do Serpro, o guia RNP/RAPSign descreve um fluxo OAuth contra o endpoint `psc-neoid.estaleiro.serpro.gov.br`, exigindo certificado SSL ICP-Brasil para configurar o servidor e credenciais client ID/secret emitidas pelo Serpro — [RNP, "Configurar certificado em nuvem do SERPRO no RAPSign"](https://ajuda.rnp.br/diplomas-digitais/passo-a-passo/configurar-certificado-em-nuvem-do-serpro-no-rapsign/configurar-certificado-em-nuvem-do-serpro-no-rapsign-manual)
- Um estudo técnico preliminar de instituto federal registrou vantagem de custo do e-CPF em nuvem (~R$89,90) frente a modelos com token (R$150-413) em pesquisa de preços de mercado, mas também observou que a opção em nuvem não era suportada oficialmente por determinado sistema de um tribunal trabalhista — mostrando que compatibilidade de sistema ainda é uma barreira prática — [Estudos técnicos preliminares citados em busca, STM/TRT]

### Inferences
- A arquitetura normativa do ITI (PSC credenciado + LPSC + HSM FIPS 140-2 nível 3) é funcionalmente análoga ao modelo europeu de "remote qualified signature" (ex.: CSC/eIDAS), mas foi construída como extensão proprietária do arcabouço ICP-Brasil já existente, em vez de adotar o padrão internacional CSC — isso explica por que não há evidência de interoperabilidade CSC no Brasil.
- Para o caso de uso via app móvel + OTP (ex.: birdID, SerproID), o certificado em nuvem efetivamente elimina tanto o hardware físico (token/smartcard) quanto a necessidade de extensão de navegador local, pois a autorização ocorre fora do navegador (no app do celular) — mas para integrações automatizadas/sistêmicas (ex.: um ERP assinando em lote), ainda é necessário implementar o fluxo OAuth/API específico de cada PSC (ex.: NEOID do Serpro), o que é uma forma diferente de complexidade de integração, não eliminada, apenas deslocada do navegador para o backend.

### Gaps
- Não foi possível localizar nesta pesquisa documentação técnica detalhada e oficial do Safeweb Nuvem ou do Soluti Nuvem (modalidade corporativa, distinta do birdID pessoa física) descrevendo APIs de integração — apenas o birdID (Soluti) e o SerproID (Serpro/NEOID) tiveram documentação de fluxo técnico encontrada.
- Não foi encontrada confirmação atualizada sobre a promessa citada em notícia de 2025 de emissão gratuita/autoassistida de certificado em nuvem para pessoas físicas pelo ITI — essa informação vinha de uma notícia e não de texto normativo, e seu status vigente em 2026 não foi verificado nesta pesquisa.

## Qual mecanismo é hoje o padrão de mercado real entre as plataformas brasileiras de assinatura eletrônica?

### Takeaway
As evidências coletadas apontam para um padrão de mercado híbrido e fragmentado — não um único "padrão" dominante: para assinatura com certificado ICP-Brasil dentro do navegador, o padrão de fato é "extensão de navegador + aplicativo nativo local" (replicado por Lacuna/Web PKI, Senior, BRy, Certisign, Vero Signare, SyngularID, GFSIS), enquanto grandes plataformas de assinatura eletrônica como a Clicksign tratam o certificado ICP-Brasil (A1, A3 local ou em nuvem) como apenas uma das várias opções de autenticação, ao lado de métodos mais simples (selfie, SMS, WhatsApp, Pix) que não exigem certificado digital algum.

### Cited Findings
- A Clicksign permite assinar documentos com certificados digitais A1 e A3 de pessoas físicas, que podem estar armazenados em dispositivos locais ou na nuvem — [Clicksign, blog oficial](https://www.clicksign.com/en/blog/o-papel-das-plataformas-de-assinatura-eletronica-e-o-ecossistema-icp-brasil)
- Na Clicksign, o usuário escolhe entre múltiplos métodos de autenticação na hora de assinar: certificado digital (grátis ou pago), selfie dinâmica, código via WhatsApp, SMS ou Pix — [Cora, "Como funciona a Clicksign?"](https://www.cora.com.br/blog/clicksign-como-funciona/)
- Jurisprudência do TJBA considerou válida, para fins de representação processual, uma procuração assinada eletronicamente por plataforma privada sem certificação ICP-Brasil, desde que acompanhada de elementos que assegurassem autenticidade e integridade — reforçando que, legalmente, o certificado ICP-Brasil não é obrigatório para boa parte dos contratos no Brasil (Lei 14.063/2020 admite qualquer modalidade entre partes que aceitem) — [Legjur, TJBA Doc. 924.1100.5740.2746](https://www.legjur.com/jurisprudencia/eme/924.1100.5740.2746)
- Para os casos em que o certificado ICP-Brasil é exigido (ex.: peticionamento judicial, NF-e, Receita Federal, cartórios), o padrão tecnológico identificado em múltiplos fornecedores independentes — Lacuna/Web PKI (via guia de terceiro eideasy), Senior SIGN Studio, BRy Signer, Certisign WebSigner, Vero Signare, SyngularID, GFSIS — é consistentemente "extensão de navegador que delega a um aplicativo/processo nativo local instalado no sistema operacional, geralmente via Chrome Native Messaging" — [eideasy, "Get Started with Lacuna"](https://www.eideasy.com/help/get-started-lacuna); [Documentação Senior](https://documentacao.senior.com.br/seniorxplatform/manual-do-usuario/sign-studio/certificado-digital/ativacao-agente-desktop.htm); [ExtensionAuditor, Vero Signare](https://extensionauditor.com/scan/vero-signare-webpki-gacmlpfmhfphdmjpbhhidbkjceoocmka)
- Órgãos públicos continuam adquirindo tokens/cartões físicos A3 via licitação (editais do Judiciário citam SafeNet 5110 como exigência de compatibilidade de sistema), ao mesmo tempo em que outros estudos técnicos preliminares passaram a considerar certificado em nuvem como alternativa economicamente mais vantajosa — evidenciando coexistência, não substituição total — [TRT7, ETP Certificados Digitais A3](https://www.trt7.jus.br/files/contas_publicas/licitacoes/pregao_eletronico/2024/PE_10_2024/011-DOCUMENTO-ETPCertificadosDigitaisA3Cert-JusInstitucionaleMagistradoetoken.pdf)
- Um fornecedor (DocuSign Brasil) cita, em blog comercial, que em janeiro de 2026 o Brasil tinha 15,7 milhões de certificados digitais ativos, com crescimento superior a 10% ao ano (dados atribuídos a ITI/ANCD, mas não verificados na fonte primária) — [DocuSign Brasil, blog](https://www.docusign.com/pt-br/blog/como-assinar-documento-com-certificado-digital)

### Inferences
- Não existe um único "padrão de mercado" absoluto; existem dois padrões coexistentes e bem estabelecidos, cada um dominante em seu segmento: (1) extensão+agente nativo local para cenários que exigem ICP-Brasil forte dentro do navegador (jurídico, fiscal, cartorial, ERPs corporativos), e (2) certificado em nuvem via app móvel para cenários de mobilidade e simplificação (pessoa física, Receita Federal, plataformas modernas). Grandes plataformas de e-signature voltadas a contratos comerciais (Clicksign) tratam ambos como apenas uma opção entre várias, priorizando métodos sem certificado quando a lei permite.
- Entre as soluções de extensão+agente nativo, a Lacuna Web PKI aparece como a mais citada e com o ecossistema de documentação/SDK mais maduro (múltiplas linguagens, pacote npm oficial, guias de terceiros como eideasy), o que é consistente com a afirmação do usuário de que é "a solução de extensão de navegador mais citada no Brasil" — embora não tenha sido possível confirmar isso com dados quantitativos de market share.

### Gaps
- Não foi possível obter dados quantitativos de market share entre os diferentes fornecedores de extensão (Lacuna, BRy, Certisign, Soluti) ou entre o modelo extensão+agente vs. nuvem, para nenhum segmento de mercado específico.
- Não foi encontrada nenhuma fonte que comparasse diretamente, de forma neutra e com números, Autentique, DocuSign Brasil e Clicksign quanto ao suporte a certificado ICP-Brasil — apenas a Clicksign teve informação técnica verificável nesta pesquisa.

## Como funciona especificamente o "Web PKI" da Lacuna Software — é extensão de navegador pura, ou extensão + aplicativo complementar local?

### Takeaway
O Web PKI da Lacuna Software é uma arquitetura de duas peças: uma extensão de navegador (disponível para Chrome, Firefox e outros via Chrome Web Store/stores equivalentes) que, por si só, é insuficiente — ela precisa de um aplicativo nativo complementar ("companion app") instalado no sistema operacional via instalador MSI/winget no Windows (há também um app para macOS), e só com os dois componentes instalados o sistema fica "totalmente instalado"; o acesso a certificados A1 (repositório de certificados do sistema/arquivo .pfx importado) e A3 (token/smartcard via driver PKCS#11) passa pelo mesmo componente nativo, exposto ao JavaScript da página via um pacote/SDK oficial (`web-pki` no npm).

### Cited Findings
- A extensão Web PKI da Lacuna, segundo um guia de terceiro (eideasy) para configurar o "Lacuna Middleware", exige duas etapas: (1) adicionar a extensão Web PKI pela Chrome Web Store, e (2) ao abrir a extensão, se aparecer a mensagem "Application not fully installed" (Aplicação não totalmente instalada), seguir o link para baixar e instalar o aplicativo nativo complementar exigido — [eideasy, "Get Started with Lacuna Middleware"](https://www.eideasy.com/help/get-started-lacuna)
- A descrição oficial da extensão na Chrome Web Store afirma que o Web PKI "permite a assinatura de documentos no navegador com os certificados do usuário, sem a necessidade de Java" — [Chrome Web Store, listagem Web PKI](https://chromewebstore.google.com/detail/dcngeagmmhegagicpcmpinaoklddcgon)

### Inferences
- A arquitetura da Lacuna Web PKI é o modelo "extensão de navegador + processo nativo local" descrito de forma consistente em toda a seção de mecanismos de mercado — a extensão por si só não tem capacidade de acessar nem o keystore do sistema (para A1) nem o driver PKCS#11 de um token (para A3); toda a operação criptográfica real ocorre no aplicativo nativo instalado separadamente, e a extensão apenas repassa a comunicação entre a página web (via o SDK `web-pki`) e esse processo local.
- O enum `InstallationStates` no SDK oficial é evidência de que a própria Lacuna projeta o fluxo de integração web assumindo que a extensão pode estar presente sem o app nativo (e vice-versa) — ou seja, a dependência de dois componentes separados é uma característica de design conhecida e tratada explicitamente na API, não um detalhe de implementação incidental.
